# 0731 史记 · 技术架构

2026-09-14 · 面向开发
配套文档：[产品设计说明](产品设计说明.md)（业务逻辑与用户流程）、[单群重构与话聚会方案](单群重构与话聚会方案.md)

> **v2 修订（2026-09-14）**：形态从"桌面客户端 + 全本地"改为"**Web 为主 + 小程序分享 + 一次性桌面导出工具**"。
> 原方案把"全本地"当成不可动摇的前提，忽略了这个产品本质是**群共享**的——全本地意味着每个群友都要自己导一遍才能看，群的社交属性不成立。
> 修订后的核心是：**一个人导一次，全群都能看。**

---

## 0. 形态：为什么是 Web + 小程序，而不是客户端

### 0.1 三段式

```
  取数（一次性）              整理（服务端）           看与分享（长期）
  ─────────────              ────────────            ──────────────
  桌面导出工具        ──►    解析 · 人脸 · 聚类   ──►  Web（主）：图库/时间线/管理
  群里一个人做一次            策展 · 索引              小程序（轻）：群友点开就看
```

关键判断：**取数和用数必须分开。** 取数只能在桌面做（见 0.2），但它是一次性的、只需要群里一个人做；用数是长期的、全群的，必须在 Web 和微信里。

### 0.2 为什么取数必须在桌面

| 方案 | 能不能拿到八年的群消息 + 12,847 张照片 | 原因 |
|---|---|---|
| 小程序 | **不能** | `wx.chooseMessageFile` 只能让用户从聊天里**手选文件**，一次几个；读不到聊天记录本身；**PC 端不支持该 API**；iOS 上还有选不到文件的兼容问题 |
| 网页上传 | 部分可以 | 用户能上传导出好的文件包，但导出这一步仍然要在桌面完成 |
| 桌面工具 | **能** | 解密本机微信的 SQLCipher 数据库，这是唯一完整的路径 |

微信官方有「聊天记录迁移与备份」（手机 → PC 微信 / U 盘 / 移动硬盘，2025 年起支持自动备份），这能帮用户把记录集中到电脑上，**但备份文件是加密的专有格式，不是给第三方解析用的**。所以还是要解密 PC 微信的库。

### 0.3 为什么小程序不能是主形态

1. **读不到数据**（见 0.2）
2. **性能撑不住**：12,847 张照片的图库要虚拟滚动 + 三档缩略图 + 大图 FLIP 转场，小程序的渲染层做这些体验明显劣于 Web
3. **审核敏感**："聊天记录"相关类目审核严格，主功能压在小程序上风险高

**小程序的正确定位是分享载体**：群友在微信里点开就能看回忆、看照片、看名场面。不做上传、不做管理。这恰恰是小程序最强的地方——分享链路零摩擦。

### 0.4 这次修订的代价：内容上云

必须诚实地说清楚：**改成 Web 之后，内容存在服务端，不再是"只存在你自己的设备上"。**

这个取舍是成立的，因为它和微信群本身的隐私预期一致——群里发过的东西，群友本来就都看过。但产品上要做到：

- **群成员可见，非成员不可见**。访问控制以群为单位，不做公开链接。
- **静态加密存储**，密钥与业务库分离。
- **成员可隐藏自己的内容**，隐藏后对全群不可见。
- **导入者要有告知义务**：导入前明确提示"这会让全群成员看到这个群的历史内容"。
- 提供**一键删除整个群档案**，删除即物理删除。

如果坚持全本地，产品就退化成"个人的微信相册"，失去了"群"这一半。这是产品决策，不是技术决策。

## 1. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| **导出工具**（桌面） | Tauri 2 + Rust | 只做一件事：取密钥、解密、导出成标准包。包体小，跨 macOS/Windows |
| **服务端** | Python（FastAPI）或 Go | 解析、人脸、聚类、策展；Python 生态对 ML 更友好 |
| **任务队列** | Celery / Asynq + Redis | 导入是长任务，必须异步 + 可断点续跑 |
| **存储** | PostgreSQL + 对象存储（S3 兼容） | 元数据入库，媒体进对象存储，走 CDN |
| **搜索** | PostgreSQL 全文检索（中文用 zhparser）或 Meilisearch | 38,204 条消息的规模，PG 足够 |
| **人脸** | InsightFace / ArcFace（ONNX Runtime，GPU 可选） | 服务端批量推理，比端上快一个量级 |
| **语音转写** | faster-whisper | 中文可用，批处理 |
| **Web 前端** | 原生 JS 或 Svelte/Solid | 现有原型是原生的；图库要跑满 60fps，避免虚拟 DOM 开销 |
| **小程序** | 原生小程序 或 Taro | 只承载浏览，逻辑轻 |

```
┌─────────────────────────────────────────────────┐
│  Web 前端（主）                                   │
│  首页策展 · 图库 · 时间线 · 话 · 聚会 · 管理        │  ← 现有原型就是这层
└───────────────────────┬─────────────────────────┘
                        │ HTTPS / JSON
┌───────────────────────┴─────────────────────────┐
│  服务端                                           │
│  ingest/      导出包校验、解包、入库               │

│  understand/  人脸、转写、文本分析                 │
│  cluster/     事件、地点、旅程、聚会               │
│  curate/      评分、回忆生成、首页编排             │
│  auth/        群成员身份与访问控制                 │
└───────────────────────┬─────────────────────────┘
                        │

```

**桌面工具的职责边界要划清楚**：只负责"把数据从微信里拿出来、打成标准包"，不做任何解析、识别、聚类。这样它可以做得非常小、非常稳定，也便于将来替换成别的取数方式（比如微信哪天开放了导出接口）。

## 3. 导入流水线

分两段跑，**每个阶段幂等、可断点续跑**。

**桌面段（导出工具，一次性）**

```
S0  定位          找到 xwechat_files/<wxid>/db_storage，列出约 26 个 db
S1  取密钥        从微信进程内存提取，每个 db 一组 (key, salt)
S2  拷贝          把加密库复制到工作区，绝不原地操作微信的文件
S3  解析消息      读 message_*.db（分片）+ session.db，转统一消息模型
S4  媒体落地      dat 还原为 jpg/mp4，silk 解码为 wav
S5  打包上传      messages.jsonl + media/ + manifest.json，分片续传
```

导出包格式（服务端只认这个，与微信版本解耦）：

```
export-<groupid>-<timestamp>.tar
├ manifest.json      群信息、成员、时间范围、条目数、各文件 sha256
├ messages.jsonl     一行一条统一消息模型
└ media/             原始媒体，文件名 = 内容 sha256
```

**服务端段（每次导入触发）**

```
S6  校验解包      校验 sha256 与 manifest，拒绝损坏包；按 wx_msg_id 幂等去重
S7  元数据        EXIF、pHash、尺寸、时长、三档缩略图 → 对象存储
S8  理解          人脸检测与特征、语音转写、文本分词与句式标注
S9  聚类与策展    事件 → 地点 → 旅程 → 聚会；评分 → 回忆 → 首页编排
```

12,847 张照片 + 38,204 条消息的规模下，桌面段约 10–20 分钟，服务端段（带 GPU）约 10–15 分钟。两段都要能断点续跑：桌面段断了重连续传，服务端段按 `job.cursor` 接着算。

### 任务状态表

```sql
CREATE TABLE job (
  id           INTEGER PRIMARY KEY,
  stage        TEXT NOT NULL,          -- S0..S7
  status       TEXT NOT NULL,          -- pending|running|done|failed
  cursor       TEXT,                   -- 断点：上次处理到的 msg_id / 文件路径
  total        INTEGER,
  done_count   INTEGER,
  error        TEXT,
  updated_at   INTEGER NOT NULL
);
```

前端的"解析中"进度环和滚动日志，就订阅这张表的变更事件。

### S1 取密钥的实现要点（桌面工具内）

```rust
// 伪代码。三种策略按可用性降级，失败时给出明确的权限引导，不要静默失败
fn acquire_keys(pid: u32) -> Result<HashMap<DbName, DbKey>> {
    if let Ok(k) = frida_hook_pbkdf(pid) { return Ok(k); }   // 首选：hook CCKeyDerivationPBKDF
    if let Ok(k) = scan_task_memory(pid) { return Ok(k); }   // 次选：Mach VM 扫 x'<64hex><32hex>'
    Err(NeedPermission)                                       // 引导用户授权，而不是报"导入失败"
}
```

拿到 key 后用 `PRAGMA key = "x'<hex>'"` + `PRAGMA cipher_page_size`、`kdf_iter = 256000`、`cipher_hmac_algorithm = HMAC_SHA512` 打开。**参数对不上会读成空库而不是报错**，所以 S1 结束必须做一次 `SELECT count(*) FROM sqlite_master` 校验。

### S3 的坑（桌面工具内）

- **消息库是分片的**（`message_0.db`、`message_1.db`…），要按 `talker` + 时间合并后重排。
- **转发的图片没有 EXIF**，拍摄时间只能退回发送时间。统一消息模型里必须同时保留 `sent_at` 和 `taken_at`，事件聚类用 `taken_at`，对话时间线用 `sent_at`。混用会让"那天的照片"对不上"那天的对话"。
- 撤回、引用、@ 这些关系存在扩展字段里，解析时要一并落库，否则名场面的"被回复次数"没法算。

## 4. 数据模型

只列核心表。全部建在自有库里，不回写微信。

```sql
-- 统一消息
CREATE TABLE message (
  id          INTEGER PRIMARY KEY,
  wx_msg_id   TEXT UNIQUE,            -- 微信原始 id，用于幂等重导
  sender_id   INTEGER NOT NULL REFERENCES person(id),
  sent_at     INTEGER NOT NULL,       -- 发送时间（秒）
  type        TEXT NOT NULL,          -- text|image|video|voice|file|link|location|system|redpacket
  body        TEXT,                   -- 文本内容或结构化 JSON
  quote_id    INTEGER REFERENCES message(id),
  revoked     INTEGER DEFAULT 0
);
CREATE INDEX idx_msg_time ON message(sent_at);
CREATE VIRTUAL TABLE message_fts USING fts5(body, content=message, content_rowid=id);

-- 媒体
CREATE TABLE media (
  id          INTEGER PRIMARY KEY,
  message_id  INTEGER REFERENCES message(id),   -- 来自哪条消息（可空：相册同步进来的）
  kind        TEXT NOT NULL,          -- photo|video|voice|file
  path        TEXT NOT NULL,
  taken_at    INTEGER,                -- EXIF 拍摄时间，缺失则为 NULL
  lat REAL, lon REAL,
  width INTEGER, height INTEGER, duration REAL, bytes INTEGER,
  phash       BLOB,                   -- 感知哈希，去连拍用
  quality     REAL,                   -- 清晰度/曝光综合分
  score       REAL                    -- 精选度（见 §5.1）
);
CREATE INDEX idx_media_taken ON media(taken_at);
CREATE INDEX idx_media_score ON media(score DESC);

-- 人物：出镜身份与发言身份分开存，靠 person 关联
CREATE TABLE person (
  id          INTEGER PRIMARY KEY,
  name        TEXT,                   -- 用户命名，未命名为 NULL
  wxid        TEXT,                   -- 发言身份
  joined_at   INTEGER,
  left_at     INTEGER,
  avatar_path TEXT
);
CREATE TABLE face (
  id          INTEGER PRIMARY KEY,
  media_id    INTEGER NOT NULL REFERENCES media(id),
  bbox        TEXT NOT NULL,
  embedding   BLOB NOT NULL,          -- 512 维 f32
  cluster_id  INTEGER,                -- 聚类结果
  person_id   INTEGER REFERENCES person(id),  -- 用户确认后才写
  confirmed   INTEGER DEFAULT 0
);

-- 事件 / 旅程 / 地点
CREATE TABLE event (
  id INTEGER PRIMARY KEY,
  started_at INTEGER, ended_at INTEGER,
  place_id INTEGER REFERENCES place(id),
  trip_id  INTEGER REFERENCES trip(id)
);

-- 名场面
CREATE TABLE highlight (
  id INTEGER PRIMARY KEY,
  start_msg_id INTEGER NOT NULL REFERENCES message(id),
  end_msg_id   INTEGER NOT NULL REFERENCES message(id),
  title TEXT, score REAL,
  reply_count INTEGER, reaction_count INTEGER, requote_count INTEGER
);

-- 聚会
CREATE TABLE gathering (
  id INTEGER PRIMARY KEY,
  proposed_at  INTEGER NOT NULL,      -- 召集句发出的时间
  scheduled_at INTEGER,               -- 约定的时间（可空）
  place TEXT,
  status TEXT NOT NULL,               -- done|missed|open
  proposer_id  INTEGER REFERENCES person(id),
  highlight_id INTEGER REFERENCES highlight(id),   -- 约的那段对话
  event_id     INTEGER REFERENCES event(id),       -- 成行时关联的事件（照片从这里来）
  corrected    INTEGER DEFAULT 0      -- 用户手动改过，之后不再被自动覆盖
);
CREATE TABLE gathering_person (
  gathering_id INTEGER NOT NULL,
  person_id    INTEGER NOT NULL,
  responded    INTEGER DEFAULT 0,     -- 应约
  attended     INTEGER DEFAULT 0,     -- 到场（由照片锚定推出）
  PRIMARY KEY (gathering_id, person_id)
);
```

鸽王榜就是 `gathering_person` 上的一次聚合，不另建表。

## 5. 关键算法的工程实现

### 5.1 精选度评分

```
score = 0.22·quality + 0.20·social + 0.18·people
      + 0.15·scarcity + 0.13·milestone + 0.12·composition − redundancy
```

- `quality`：拉普拉斯方差归一化 + 曝光直方图偏度。**微信压缩过的图统一乘 0.85**，否则首页会被转发图占满。
- `social`：回复数、引用数、表情回应数、被保存后重发次数，各自对数归一后加权。这是本产品独有的信号，也是最强的。
- `scarcity`：按所在月份的内容密度取倒数并归一，防止内容最多的那一年霸屏。
- `redundancy`：pHash 汉明距离 < 8 且 `taken_at` 相差 < 3s 视为连拍，组内只留最高分，其余乘 0.1。

一票否决（直接 `score = 0`）：截图、二维码图、聊天记录截图、表情包、宽高比 > 3:1、用户已隐藏、含已屏蔽人物。

### 5.2 事件聚类

一维时间序列上的密度聚类，**间隔阈值动态**：白天（08–22 时）4 小时，夜间 8 小时。

切分后做两次校正：
- 同簇内 GPS 跨度 > 30km，或出镜人物集合交集 < 30% → 拆成两个事件
- 相邻簇地点相同且人物高度重合 → 合并，即使跨过午夜（凌晨两点还在拍的那个夜晚属于前一天）

### 5.3 人脸聚类

同一个人八年里外形变化很大，直接全局聚类会把一个人拆成好几组。做法：

1. 按 18 个月为窗口分段，段内用 HDBSCAN 聚类（`min_cluster_size = 3`）
2. **跨段桥接**：两个相邻段的簇，若在同一批照片里从未同时出现过、且中心特征余弦距离 < 0.42（比段内阈值放宽），判为同一人
3. 增量：新导入的脸先与已有簇中心比对，超阈值才新建簇，不重跑全量

**永远不自动写 `person_id`**，只产出建议。合并线索按可信度排序：该成员发的自拍（发送者 = 图中唯一人脸）> @ 与被回复关系 > 昵称与图中文字 > 用户手动。误合并两个人的体验损伤远大于漏合并。

### 5.4 聚会识别

**用规则引擎，不用大模型。** 理由：可解释、可调阈值、离线、零成本，而且这类句式高度模板化，规则的召回率已经够用。

```
Step 1  召集句捕捉
        {时间词} + {聚集动词}，或带 ? 的提议句
        时间词：绝对（周六|10月1号|下周三）+ 相对（明天|后天|下周）
        聚集动词：吃饭|聚|约|见|走起|来|出来

Step 2  应答聚类 ← 最强信号
        召集句后 30 分钟内，≥3 条短肯定句（来|+1|算我一个|收到|好|👍，长度 ≤ 6）
        这个模式在日常闲聊里几乎不出现，误报率很低

Step 3  时间地点收敛
        提议到应答之间的消息里抽最终时间和地点，多候选取最后一次提及

Step 4  照片锚定
        scheduled_at ± 6h 内是否有照片涌入
        有 → status = done，关联该 event，到场者 = 那批照片里出现的人
        无 → status = missed
        scheduled_at 在未来 → status = open
```

**到场判定不能只看照片里的脸**，还要并上那个时间窗内在群里发过消息且带位置特征的人，否则不爱入镜的人永远是"没到场"。

每条识别结果都要能在详情页手动修正，修正后置 `corrected = 1`，后续重跑不覆盖，并作为负样本调整该库的阈值。

### 5.5 名场面选取

```
score = 0.30·密度 + 0.28·被回复 + 0.22·表情回应 + 0.20·后续被重提
```

- 密度：该片段内 `消息数 / 时长`，相对全库中位数归一
- 被重提：后续消息中出现该片段关键词的次数（"还记得那次说要去西藏吗"）
- 边界确定：以峰值消息为中心，向两侧扩展到消息间隔 > 5 分钟为止，上限 10 条

标题生成是唯一适合上小模型的地方（本地 1–3B 量化模型足够），但要能降级：模型不可用时退回"日期 + 参与人数"这种模板标题。

## 6. 前端架构

### 6.1 现有原型的模块划分可以直接映射

```
shell      应用外壳、路由、全局事件委托
hero       首页 hero 轮播
memories   为你回忆 / 最近的日子
people     人物 / 旅程 / 地点
shelf      媒体类型 / 这一年的这一天 / 相簿 / 群小传
talks      聚会 / 名场面 / 「话」视图
library    图库四视图
messages   消息时间线
overlays   看图器 / 回忆播放器 / 上传 / 管理
login      账号
```

每个模块自带 CSS 前缀和一个 `initXxx()`，跨模块只通过 `data-*` 约定通信（`js-photo`、`js-memory`、`js-goto`、`js-gathering`…）。这套约定在真实工程里换成组件 props 或事件总线即可，边界是现成的。

### 6.2 必须重写的：图库虚拟滚动

**这是原型和真实产品差距最大的地方。** 现在图库里是几十个写死的 `<img>`，真实场景是 12,847 张。必须：

- 虚拟列表：只渲染视口 ± 2 屏的格子，其余用占位撑高度
- 三档缩略图：`s` 200px（全部视图）、`m` 600px（日/月视图）、`l` 1600px（看图器），按当前密度选档
- 滚动时只加载 `s`，停止滚动 150ms 后再补 `m`
- `content-visibility: auto` + `contain-intrinsic-size` 兜底

目标：8000 张照片的"全部"视图滚动保持 60fps，内存不超过 400MB。

### 6.3 其余可直接复用

设计 token 体系、动效（Ken Burns / FLIP 转场 / 滚动揭示）、四个叠层的交互、响应式断点、无障碍处理，都是成品，照搬即可。

## 7. 隐私与访问控制

形态改成 Web 之后，内容在服务端，**"只存在你自己的设备上"这句承诺不再成立**。取而代之的模型是：**这是一份群共享的档案，边界就是这个群**。

### 7.1 访问控制

- **以群为单位授权**，不提供公开链接。非成员拿到 URL 也打不开。
- **成员身份怎么确立**：导入者建立群档案后生成邀请码，群友凭邀请码加入并绑定自己的账号；同时把他在聊天记录里的 `wxid` 与账号关联，这样他才能"认领"自己的人物卡和隐藏自己的内容。
- **退群成员**：历史内容保留（群的记忆是完整的），但失去访问权。
- **导入者的告知义务**：导入前必须明确提示"这会让全群成员看到这个群的历史内容"，并要求勾选确认。这一步不能省。

### 7.2 成员的控制权

- **隐藏自己的内容**：任何成员可以把自己发的某条消息、某张照片设为全群不可见。
- **退出并清除**：成员可以要求把自己的人脸数据和人物卡从档案里移除。
- **一键删除整个群档案**：导入者可发起，删除即物理删除（媒体 + 元数据 + 派生数据），不做软删除。

### 7.3 存储与传输

- 传输全程 HTTPS；媒体走带签名的临时 URL，有效期不超过 15 分钟，不允许猜测遍历。
- 对象存储**静态加密**，密钥托管在 KMS，与业务库分离。
- 人脸特征向量属于生物识别信息，**单独加密存储、单独授权**，且不与任何外部服务共享。
- 日志里不记录消息正文、媒体路径和人脸向量。

### 7.4 桌面导出工具

- **绝不碰微信的原始文件**：一律拷贝到工作区再只读打开。
- **取密钥的权限要显式说明**：用一屏讲清楚为什么需要、密钥用在哪、不会上传密钥本身（只上传解出来的内容）。含糊其辞会让用户直接放弃。
- 导出包上传后，本地工作区的明文副本要**主动清理**，并提示用户导出包的位置。

### 7.5 合规边界

只处理用户本人所在群的数据，由群成员本人发起导入；不做批量采集、不做他人数据抓取、不用于训练任何对外模型。产品内要有明确的使用声明。

| 存储 | 无 | PostgreSQL + 对象存储 |
| 小程序 | 无 | 浏览端，复用同一套 API |

## 9. 建议的里程碑

| 阶段 | 交付 | 验收标准 |
|---|---|---|
| **M0 取数可行性** | 一个跑通的命令行脚本 | 在目标 macOS / Windows 版本上把一个真实群完整导出成标准包。**这一步的结论可能改变整个项目形态，必须最先做** |
| M1 导出工具 | Tauri 壳 + S0–S5 + 上传 | 普通用户能独立完成一次导出，断点续传不丢数据，权限引导清晰 |
| M2 服务端打通 | S6–S7 + 图库（虚拟滚动） | 12,000 张照片滚动 60fps，三档缩略图生效 |
| M3 自动整理 | S8–S9 的事件/地点/旅程 + 首页 | 首页板块全部由真实数据驱动 |
| M4 群与权限 | 邀请码、成员绑定、隐藏与删除 | 非成员无法访问；成员能隐藏自己的内容 |
| M5 人物 | 人脸聚类 + 合并建议 UI | 群成员识别准确率可接受，误合并为 0 |
| M6 话与聚会 | 名场面 + 黑话 + 聚会识别 + 鸽王榜 | 人工抽查 20 次聚会，识别正确率 ≥ 80% |
| M7 小程序 | 浏览端 + 分享卡片 | 群友在微信里点开能看回忆、照片、名场面 |

**M0 是整个项目的前置条件。** 它不通，后面全都不用做；它通了但需要用户关 SIP 这类操作，产品形态也要重新设计（比如退而求其次，只支持微信官方备份能覆盖的范围）。
