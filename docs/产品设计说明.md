# 0731 史记 · 产品设计说明

原型地址：`html/index.html`（单文件，双击即可打开）
最后更新：2026-09-14

---

## 速览

**一句话**：把微信群里沉淀多年的照片、视频、语音、文件和对话导进来长期保存，并像苹果相册一样自动整理成可以回看的记忆。

**它解决的问题**：一个攒了八年的老友群，里面有一万多张照片、三万多条消息。这些东西事实上已经丢了——不是删了，是翻不到。微信的聊天记录是一条线性的流，没有索引、没有聚合、没有人物、没有地点，往上翻十分钟只能翻到三个月前。

**产品的两面**：
- **像 QQ 空间的一面**：以"群"为单位的社交记忆。谁说了什么、谁和谁常同框、这个群的性格是什么。
- **像苹果相册的一面**：自动生成的回忆影片、人物识别、地点聚类、年月日图库。

**最关键的设计判断**：这个产品的价值不在"存下来"，在"自动整理"。用户不会手动打标签、建相簿、写说明。所以首页必须是系统替用户做完判断之后的结果，而不是一个等着用户去组织的空文件夹。

## 一、完整业务逻辑

### 1.1 数据链路

```
原始素材                  解析与归一                   理解与聚类                  策展与呈现
─────────                ──────────                  ──────────                 ──────────
微信聊天记录导出   ──┐                                ┌─ 事件聚类（切成"天"和"次"）
群内图片/视频     ──┤                                ├─ 人物识别（脸 + 发言人合并）
语音（silk/amr）  ──┼──►  统一消息模型  ──►  索引  ──┼─ 地点聚类（GPS + 逆地理）      ──► 首页自动策展
文件/链接/位置    ──┤     + 媒体元数据                ├─ 旅程判定                        图库/时间线
手机相册同步      ──┘     + EXIF/GPS                  └─ 精选度评分                      回忆影片
```

四段拆开说：

**第一段 · 素材进来。** 三个入口：导入微信聊天记录（主力）、直接上传文件、从手机相册同步。其中聊天记录是这个产品独有的部分——它带来的不只是图片，还有图片**被发出时的上下文**（谁发的、几点、旁边的人说了什么），这是普通相册永远没有的信息。

**第二段 · 解析归一。** 把微信那套异构格式转成统一的消息模型：每条消息有发送者、时间戳、群、类型、内容体、引用关系。媒体文件抽出 EXIF（拍摄时间、GPS、设备）。语音做转写。链接抓标题和缩略图。

这一段有个容易被忽略的坑：**微信转发的图片会丢 EXIF**，拍摄时间只能退回到"发送时间"。所以时间轴上要区分"拍摄时间"和"发送时间"，事件聚类用前者，对话时间线用后者。

**第三段 · 理解与聚类。** 这是自动整理的核心，四件事同时做：事件聚类、人物识别、地点聚类、精选度评分。规则见第二节。

**第四段 · 策展与呈现。** 用上一段的结构化结果，生成首页的十个板块、图库的四种视图、回忆影片的候选池。

### 1.2 数据从哪来——这是真正的卡点

必须说清楚：**微信没有开放任何获取个人微信群聊记录的 API**。公众号、开放平台、小程序都没有。企业微信有会话存档接口，但只覆盖企业微信的会话。

所以现实中可行的路径只有一条：**从 PC 版微信的本地数据库导出**（解密后提取图片、语音、文件、消息），也就是 WeChatMsg 这类开源工具在做的事。这意味着真实形态是"本地客户端 + 本地存储"，而不是"网页扫码登录后云端自动同步"。

这个判断反过来影响了产品设计：
- 首页的「导入微信聊天记录」做成了分步引导（选群 → 选时间范围 → 解析 → 自动整理），而不是一个"一键同步"开关。
- 取数只能在桌面完成，但**只需要群里一个人做一次**，全群共享结果。形态因此是「桌面导出工具 + Web + 小程序」，不是桌面客户端（见[技术架构](技术架构.md) §0）。
- 微信登录解决不了"数据从哪来"，已否掉（见 1.3）。

### 1.3 为什么不做微信登录（已决定移除）

**结论：这个产品不需要微信登录，原型里的扫码登录已移除，改为本机账号。**

理由是它解决不了任何实际问题：数据来自本机微信数据库（见 1.2），不依赖任何微信账号体系；产品全本地运行，没有需要跨设备同步的服务端身份。真要接的话，代价是这三样：

| 需要什么 | 具体要求 |
|---|---|
| 后端服务 | `code` + `AppSecret` 换 `access_token` 必须在服务端做，`AppSecret` 不能出现在前端 |
| 备案域名 | 授权回调域要在开放平台后台登记，必须是固定的、已 ICP 备案的域名 |
| 企业资质 | 微信开放平台的开发者资质认证只认组织主体（公司或个体工商户），个人账号无法认证；大陆审核费 300 元/年 |

换来的只是一个头像和昵称。不值得。

## 二、自动策展规则

所有"系统替你做的判断"都来自这四组规则。它们共享同一套分数，所以系统在不同地方的判断是一致的——不会首页说这张好、相簿里又不推荐它。

### 2.1 精选度评分

```
精选度 = 0.22·画质 + 0.20·社交热度 + 0.18·人物权重
       + 0.15·稀缺性 + 0.13·纪念度 + 0.12·构图 − 冗余惩罚
```

| 因子 | 怎么算 |
|---|---|
| 画质 | 清晰度（拉普拉斯方差）、曝光分布、噪点。微信压缩过的图统一降权 0.85，避免首页全是转发图 |
| **社交热度** | 这张图在群里被回复、被引用、被表情回应、被保存后重发的次数。**这是微信群独有的信号，也是最强的信号**——普通相册没有它 |
| 人物权重 | 图里有几张已命名的脸、是否正脸、有无闭眼。多人合影额外加权 |
| 稀缺性 | 所在时间段的内容密度。内容最少的那几个月，同等质量的照片得分更高，防止内容最多的那一年霸屏 |
| 纪念度 | 是否落在建群纪念日、成员生日、已识别的重要事件当天 |
| 构图 | 主体是否落在三分点、水平线是否倾斜、是否有截图边框 |
| 冗余惩罚 | pHash 距离小于阈值且拍摄时间相差 3 秒内的连拍，只留最高分那张 |

**一票否决**：纯截图、二维码图、聊天记录截图、表情包、宽高比超 3:1 的长图、用户已隐藏的、含已屏蔽人物的。

### 2.2 事件聚类——怎么把一堆照片切成「一天」和「一次」

两层：

**第一层 · 时间密度切分。** 全库按时间戳排成一维序列，用密度聚类找扎堆时段。间隔阈值是动态的：白天 4 小时，夜里 8 小时。

**第二层 · 地点与人物校正。** 同一时间簇内若 GPS 跨度超 30 公里，或出镜人物交集低于 30%，切成两个事件。反过来，相邻时间簇若地点相同且人物高度重合，跨过午夜也合并——凌晨两点还在拍的那个夜晚，属于前一天。

**日子 ≠ 事件**：一个自然日可能有多个事件（白天爬山、晚上聚餐）。首页「最近的日子」按自然日展示，进入某天的详情后才按事件分节。

### 2.3 旅程判定

同时满足三条才算：

1. 事件的地理中心距**常住城市**中心超过 50 公里（常住城市取全库 GPS 众数所在行政区）
2. 连续事件序列跨过至少两个日历日
3. 至少两个已命名人物在场——一个人的出差不算旅程，归到地点

判定后向前后各扩 6 小时，把出发前的候机厅、返程的高铁站收进来。相距 50–120 公里的近郊标为"短途"，卡片略小，与远行区分。旅程详情页底部有「不是一次旅程，拆开」，用户的每次修正作为负样本调整该群的阈值。

### 2.4 人物——两套身份的合并

**微信群里"说话的人"和"照片里的人"是两套完全独立的 ID，这是这个产品最容易做错的地方。**

- **A 侧 · 出镜身份**：人脸检测 → 特征提取 → 层次聚类。同一个人八年里外形变化很大，所以按时间窗口分段聚类后再跨段桥接：两个相邻时间簇若在同一批照片里从未同时出现、且特征距离小于放宽阈值，判为同一人。
- **B 侧 · 发言身份**：微信号 / 群昵称。改过昵称的通过微信号追踪。

**合并线索**（按可信度排序）：
1. 该成员发的自拍（发送者 = 图中唯一人脸）——最强证据
2. @ 与被回复关系：「@陈屿 你这张拍糊了」发生在某张照片后 2 分钟内
3. 群昵称与照片中的文字（蛋糕上的名字、工牌）
4. 用户手动确认

**永远不自动合并，只给建议**：「这个人可能是陈屿（依据：他发过 47 张自己的自拍）」，等用户确认。误合并两个人的体验损伤远大于漏合并。

**退群成员**：历史内容全部保留，人物卡标注「已退群」，但不再进入"常在一起的人"的推荐。

### 2.5 回忆是怎么生成的

先按模板生成候选池（年度回顾、人物专题、旅程重游、主题串联、节日纪念），再用今天的触发条件给候选打分排序，取最高的几条。**一天最多换三条**，换下来的进「回忆」一级视图存档——这一条很重要，天天全换会让用户失去"我记得昨天首页那个"的连续感。

## 三、模块功能逻辑

原型共 11 个模块。前 6 个组成首页，后 5 个是一级视图与全屏叠层。

### 3.1 外壳（shell）

顶部毛玻璃导航（首页/图库/回忆/人物/地点/话）+ 搜索 + 上传 + 管理 + 账户。滚动时导航从透明渐变为毛玻璃。移动端折叠为底部 tab bar。

承担三件全局的事：**视图路由**（hash 路由，支持前进后退）、**滚动入场观察器**（IntersectionObserver + 滚动兜底 + 超时保险，保证任何环境下内容都不会卡在不可见）、**全局事件委托**（`.js-goto` / `.js-photo` / `.js-memory` 等）。

同时内含两个一级视图的完整内容：人物、地点。

### 3.2 首页 hero

全屏「今日精选」轮播。5 张大图 Ken Burns 缓慢缩放，交叉淡入。文案随图切换（「六年前的今天，我们在稻城」），带逐行上移入场。

**逻辑**：从精选度最高的一批里，优先取"今天这个日期在历史上"的照片；没有则退回本周最高分。

### 3.3 为你回忆 + 最近的日子（memories）

- **为你回忆**：横滑的 3:4 回忆卡，封面满溢 + 渐变遮罩压字。点击进全屏播放器。
- **最近的日子**：过去 30 天按自然日聚合，每张卡是当天代表照片 + 日期 + 地点 + 参与者头像 + 照片数 + 四宫格预览。

### 3.4 人物 + 旅程 + 地点（people）

首页里节奏对比最强的一段：人物是密集的小圆，旅程是巨大的 21:9 大卡，地点是宽幅横条。

- **人物**：横滑圆形头像，按出现频率排序，首位是「+ 添加人物」
- **旅程**：主卡（最近或最高分的一次）+ 三张次级卡，主卡右下角是照片堆叠，hover 展开扇形
- **地点**：左侧抽象地图（CSS/SVG 绘制，呼吸光点），右侧地点卡网格，两侧 hover 联动

### 3.5 媒体类型 + 这一年的这一天 + 相簿 + 群小传（shelf）

- **不只是照片**：视频/语音/文件/链接四个入口，各有语义色和真实统计（语音卡上画 SVG 波形，视频卡带时长角标）
- **这一年的这一天**：水平年份轴（2017–2024），点击年份展开当天大图 + 那天的一句群消息摘录（同一时刻只展开一个年份）
- **相簿**：不规则拼贴封面（所有照片/收藏/实况/截图/最近删除/隐藏）
- **群小传**：一张宽卡讲这一个群——成员头像九宫格、建群日与天数、四个关键数字、话最多/最晚睡/第一句话/最长的一次

### 3.6 图库（library）

苹果相册「图库」标签页的等价物。年/月/日/全部四种模式都真实实现：

| 模式 | 形态 |
|---|---|
| 年 | 3 列大卡，每年一张代表图 |
| 月 | 按月分组，1 大 2 小不规则拼贴 |
| 日 | 日期标题 + 当天照片的紧密等宽网格 |
| 全部 | 最密网格，密度滑块可调每行数量 |

外加：筛选侧栏（类型/群/人物/地点/时间，实时过滤）、多选模式（批量加相簿/设精选/分享/删除）、角标（视频时长、LIVE、收藏、精选）。

### 3.7 群消息时间线（messages）

**这是把微信聊天记录重新排版成"可回看的档案"的核心视图**，不是微信界面的复刻。

- 左侧：群档案头（封面虚化 + 成员 + 统计）→ 时间轴滑块（拖动跳到某年某月）→ 群内搜索 → 消息流
- 右侧：上下文面板

单群定位下没有群列表侧栏，中间栏因此更宽。

消息用"档案排版"而非气泡：头像 + 姓名 + 时间一行小字，内容块在下方左对齐，连续消息合并到同一发送者块下。覆盖全部类型：文字（含 @ 和表情）、单图、多图拼贴、视频、语音（SVG 波形 + 转写文字，播放时波形逐段点亮）、文件、链接卡、位置、引用回复、红包、系统消息。

**杀手锏功能在右侧面板**：从图库点开一张照片，能跳到这里看它当时被发出的上下文——谁发的、那天大家在说什么。照片和对话是双向可达的。这是普通相册做不到、而这个产品天然具备的能力。

### 3.8 全屏叠层（overlays）

四个，都支持 Esc 关闭、焦点陷阱、锁 body 滚动：

1. **回忆播放器**：纯黑全屏，照片 Ken Burns 自动播放（每张 4.5 秒，交叉淡入 1.2 秒），顶部分段进度条，开场标题动画，底部毛玻璃控制条（播放/暂停、日期地点、音乐、保存为影片），结尾「回忆结束」+ 重播
2. **看图器**：从缩略图 FLIP 放大到全屏，胶片条、信息面板（EXIF/人物/来源群）、「在对话中查看」按钮
3. **上传面板**：三个 tab（上传文件 / 导入微信聊天记录 / 从相册同步）+ 存储用量分段条
4. **管理面板**：右侧滑入，七个分区（素材库/人物/相簿/群与来源/标签/存储/隐私），素材库是可排序可多选的真实表格

### 3.9 账户（login）

本机账号，没有外部登录。顶栏头像点开是账户菜单：素材与人物管理、导入聊天记录、关于时光。微信登录已评估并否掉，理由见 1.3。

### 3.10 话与聚会（talks）

首页两个板块 +「话」一级视图 + 聚会详情叠层：

- **聚会**：横滑卡，成行的带封面照片，没去成的是虚线空卡。详情页上半是当时约的对话，下半是当天的照片，中间一条「这一天真的发生了」。
- **名场面**：横滑对话片段卡，一段 5～8 条的完整对话，保留接话节奏。
- **「话」视图**：五个 tab——名场面、群黑话、年度关键词、数字小传、聚会与鸽王榜。

识别规则与卡片形态见[单群重构与话聚会方案](单群重构与话聚会方案.md)。

## 四、用户流程

### 流程一 · 首次使用（最关键的一条）

```
打开 → 空状态：「还没有内容，先导入一个群」
  → 点「导入微信聊天记录」
  → 选群（列出 PC 微信里的群，显示各自消息数和时间跨度）
  → 选时间范围（默认全部）
  → 解析中：进度环 + 逐条滚动日志（「正在解析 2019 年 8 月…」「已提取 1,204 张图片…」）
  → 自动整理中：识别人物、聚类事件、判定旅程、生成回忆
  → 完成小结卡：「12,847 张照片 · 识别出 12 位人物 · 9 次旅程 · 生成 143 部回忆」
  → 首页第一次被填满
```

**这条流程的设计要点**：解析和整理可能要几分钟，所以不能只转一个圈。逐条滚动的日志让用户看到系统真的在读他的东西，完成小结卡则是第一次价值交付——用户在这一刻知道自己拿回了什么。

### 流程二 · 日常回看（最高频）

```
打开 → 首页 hero 是今天的精选（「六年前的今天，我们在稻城」）
  → 被打动 → 点「播放回忆」→ 全屏影片
  → 看完 → 「查看全部照片」→ 图库定位到那一天
  → 看到一张有意思的 → 点开看图器
  → 好奇当时发生了什么 → 「在对话中查看」→ 跳到消息时间线的那一刻
  → 看到当时群里的对话 → 顺着往下翻
```

这条路径体现了产品的完整闭环：**从被推送的记忆，到具体的照片，再到照片背后的对话**。三层之间随时可以往下钻，也随时可以横跳。

### 流程三 · 找特定内容

```
三个入口：
  搜索框    → 输入「海边」「二〇一九」「陈屿」「语音」→ 跨类型结果
  人物视图  → 点某人 → 他的所有照片 + 常同框的人 + 常去的地点
  图库筛选  → 类型 + 人物 + 地点 + 时间滑块组合过滤
```

### 流程四 · 整理与维护（低频但必要）

```
管理面板 → 人物：系统给出合并建议「这 2 组可能是同一个人」→ 确认或忽略
        → 素材库：批量打标签、设精选、隐藏、删除
        → 存储：清理建议（重复照片、模糊照片、大文件视频）
```

## 五、当前原型与真实产品的差距

| 维度 | 原型 | 真实产品需要 |
|---|---|---|
| 数据 | 内置的假数据（101 张策展照片 + 12 个人物 + 5 个群） | 本地客户端解析 PC 微信数据库 |
| 登录 | 界面演示 | 后端 + 备案域名 + 企业资质 |
| 人物识别 | 预设结果 | 人脸检测 + 特征聚类模型 |
| 事件/旅程聚类 | 预设结果 | 按第二节规则实现的聚类服务 |
| 存储 | 无 | 本地数据库 + 可选私有云备份 |
| 形态 | 网页 | 桌面客户端（macOS/Windows）更合适 |

原型的价值在于：**把"自动整理之后应该长什么样"完整地定义出来了**。所有板块的信息层级、卡片形态、交互路径、文案口径都已经确定，后端按这套规则产出数据即可。

## 附：技术说明

- 单文件 HTML，原生 HTML/CSS/JS，无框架无依赖，双击即可打开
- 约 917 KB（gzip 后约 176 KB），配 15 MB 图片素材
- 深色沉浸设计，完整的 CSS 变量体系（背景 5 层、文本 4 级、圆角 6 档、动效曲线 4 条）
- 响应式四档（1440 / 1024 / 768 / 430），移动端底部 tab bar
- 无障碍：焦点可见样式、焦点陷阱、aria 属性、`prefers-reduced-motion` 兜底
